# Writing a Hook

A hook is a single transformation applied to a path during a sync. Hooks form
an ordered pipeline: on **push** they run in declaration order before the
content is uploaded, and on **pull** they run in reverse order after the content
is downloaded. Built-in hooks are Zip (compression), Encryption (AES-256-GCM),
and Backup (rotated replicas).

This guide walks through adding a new hook end to end.

## The `Hook` trait

Every hook implements a single method:

```rust
pub trait Hook: std::fmt::Debug + Send + Sync {
    fn process(&self, ctx: HookContext, cfg: &AppConfig) -> anyhow::Result<HookContext>;
}
```

`process` receives the current [`HookContext`] and returns an updated one. The
important field is `ctx.path`: it is the value each hook reads and rewrites. A
transforming hook writes its output to a new (usually temporary) location and
returns `ctx.with_path(new_path)`. Hooks that do not change the payload (like
Backup) return the context unchanged.

## `HookContext`

`HookContext` is the state threaded through the pipeline for one sync:

| Field           | Purpose                                                        |
| --------------- | ------------------------------------------------------------- |
| `path`          | Current working path; rewritten by each transforming hook.    |
| `rclone_path`   | Path to the `rclone` binary (for hooks that call rclone).     |
| `remote_config` | The target [`Remote`].                                        |
| `path_config`   | The [`PathConfig`] driving the sync.                          |
| `metadata`      | Free-form map for passing values between hooks.               |

Use `metadata` to communicate between hooks or with the sync engine. Keys are
[`HookContextMetadata`] variants (e.g. `ZipChecksum`, `CalculatedHash`).

## Anatomy of a hook

Each built-in hook lives in its own module under `src/hooks/<name>/`:

```
src/hooks/<name>/
├── mod.rs      # re-exports
├── hook.rs     # define_hook! + impl Hook
├── config.rs   # impl HookBuilderTrait (interactive setup)
└── <name>_hook.rs  # the actual transformation logic (optional split)
```

Two paired types back every hook, generated by the [`define_hook!`] macro:

- `XHookConfig` — serializable, stored in the registry JSON. Always has an
  `exec: HookExecType` field plus whatever configuration you declare.
- `XHook` — the runtime struct with the same fields, produced from the config
  via a generated `From<XHookConfig>`.

## Step by step

Suppose you want a `Checksum` hook that writes a `.sha256` sidecar on push.

### 1. Declare the paired structs

`src/hooks/checksum/hook.rs`:

```rust
use crate::{
    config::prelude::{AppConfig, Hook},
    define_hook,
    hooks::prelude::HookContext,
};

define_hook!(ChecksumHook {
    algorithm: String,
});

impl Hook for ChecksumHook {
    fn process(&self, ctx: HookContext, _cfg: &AppConfig) -> anyhow::Result<HookContext> {
        anyhow::ensure!(ctx.file_exists(), "source does not exist: {:?}", ctx.path);
        // ... compute and write the sidecar, then:
        Ok(ctx) // path unchanged
    }
}
```

`define_hook!` expands to `ChecksumHookConfig { exec, algorithm }` (serde) and
`ChecksumHook { exec, algorithm }` plus the `From` conversion.

### 2. Implement the interactive builder

`src/hooks/checksum/config.rs`:

```rust
impl HookBuilderTrait for ChecksumHookConfig {
    fn build(exec: HookExecType) -> anyhow::Result<HookConfig> {
        let algorithm = inquire::Text::new("Algorithm:")
            .with_default("sha256")
            .prompt()?;
        Ok(HookConfig::Checksum(Self { exec, algorithm }))
    }
}
```

`build` is called once per selected direction (push, pull). If your hook's two
directions share setup input (like Encryption, where one password derives both
configs), also implement [`HookBuilderSharedConfigTrait`] and set
`share_config: true` in the registration below.

### 3. Register the hook

Add a variant to the [`Hooks`] enum in `src/config/hook_config.rs` and an entry
in the [`register_hooks!`] block:

```rust
Checksum {
    config: ChecksumHookConfig,
    hook: ChecksumHook,
    enum_type: Hooks::Checksum,
    modifies_name: false,
    share_config: false,
    display: |cfg: &ChecksumHookConfig, f: &mut std::fmt::Formatter|
        write!(f, "Checksum({})", cfg.algorithm),
    push_desc: "Write a checksum sidecar before uploading",
    pull_desc: "Verify the checksum after downloading",
},
```

Field reference:

| Field           | Meaning                                                            |
| --------------- | ------------------------------------------------------------------ |
| `config`/`hook` | The paired types from `define_hook!`.                              |
| `enum_type`     | The matching `Hooks` variant.                                      |
| `modifies_name` | `true` if the hook changes the output filename (see below).        |
| `share_config`  | `true` if one prompt session produces both push and pull configs.  |
| `display`       | Closure rendering the config in listings.                          |
| `push_desc`     | Help text shown when selecting the hook for push.                  |
| `pull_desc`     | Help text shown when selecting the hook for pull.                  |

### 4. Wire the module

Add `pub mod checksum;` to `src/hooks/mod.rs`, re-export the types in
`src/hooks/prelude.rs`, and reference them where `register_hooks!` is invoked.

## Filename-modifying hooks

If a hook changes the output filename, set `modifies_name: true` and extend
[`compute_remote_filename`] in `src/cli/commands/sync/utils/compute_remote_filename.rs`
to append the right extension for your `Hooks` variant. This keeps push and pull
agreeing on the remote filename (e.g. Zip appends `.zip`, Encryption appends
`.enc`). The pull side uses `modifies_filename()` to locate the downloaded file.

## Ordering and reversibility

Because pull replays the pipeline in reverse, transforming hooks should be
invertible in the opposite direction. For example: push runs `Zip` then
`Encryption` (compress, then encrypt); pull runs `Encryption` then `Zip`
(decrypt, then extract). Design your `Push`/`Pull` branches to mirror each
other.

## Testing

Add unit tests next to the transformation logic (see the `tests` module in
`src/hooks/encryption/encryption_hook.rs` for a round-trip example) and/or an
integration test under `tests/hooks/` (see `tests/hooks/zip_test.rs`). Prefer
testing the pure transformation functions directly so tests do not require
interactive prompts.
